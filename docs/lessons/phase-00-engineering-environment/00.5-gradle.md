# Lesson 1 — What Is Gradle?

Before touching commands, understand **why Gradle exists**.

Imagine a Java project containing:

```text
MyApp/
├── src/
│   ├── main/
│   │   └── java/
│   └── test/
│       └── java/
├── dependencies/
├── build/
└── ...
```

As the project grows, building it manually becomes annoying.

You would need to:

```text
find Java source files
        ↓
compile them
        ↓
find dependencies
        ↓
put dependencies on the classpath
        ↓
compile tests
        ↓
run tests
        ↓
package application
        ↓
produce JAR
```

A **build tool** automates this process.

Gradle is one of those build tools.

---

## 1. What does Gradle do?

At a high level:

> **Gradle automates the process of building, testing, and packaging software.**

For a Java project, Gradle can handle things such as:

* compiling Java code
* downloading dependencies
* compiling test code
* running tests
* creating JAR files
* cleaning generated files
* executing custom build tasks

Instead of manually doing:

```text
javac ...
java ...
```

you can eventually do:

```bash
./gradlew build
```

and Gradle coordinates the required work.

On Windows, you'll commonly use:

```powershell
.\gradlew.bat build
```

---

# 2. Why do we need a build tool?

You already learned Maven.

Maven solves this problem using a declarative configuration file:

```text
pom.xml
```

Gradle solves the same general problem, but uses Gradle build scripts.

A common Java Gradle project contains:

```text
build.gradle
```

or the Kotlin-based form:

```text
build.gradle.kts
```

For our apprenticeship, we'll initially focus on:

```text
build.gradle
```

because it uses the Groovy DSL and makes the fundamental Gradle concepts easier to see.

---

# 3. Gradle's job in our engineering model

Earlier we established this mental model:

```text
Computer
   ↓
Terminal / Shell
   ↓
Project files
   ↓
Git
   ↓
GitHub
   ↓
Build tool
   ↓
IDE
   ↓
Application
```

Gradle sits here:

```text
Java source code
      ↓
    Gradle
      ↓
 compile
      ↓
   test
      ↓
 package
      ↓
   JAR
```

So Gradle isn't Java itself.

It doesn't replace Java.

Instead:

```text
Java       → programming language
JDK        → tools/runtime for Java
Gradle     → build automation tool
JUnit      → testing framework
Git        → version control
GitHub     → remote collaboration platform
VS Code    → code editor
```

This distinction is important.

---

# 4. Maven vs Gradle

You just finished Maven, so this is a useful comparison.

### Maven

Configuration:

```text
pom.xml
```

Example dependency:

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>...</version>
</dependency>
```

### Gradle

Configuration:

```text
build.gradle
```

Dependency syntax is much shorter:

```groovy
dependencies {
    testImplementation 'org.junit.jupiter:junit-jupiter:...'
}
```

Both can accomplish things like:

```text
download dependencies
        ↓
compile
        ↓
test
        ↓
package
```

The major difference is **how you describe the build**.

Maven primarily uses XML configuration.

Gradle uses a build-script DSL.

---

# 5. Gradle is task-oriented

This is one of the most important concepts.

Gradle organizes work into **tasks**.

For example:

```text
compileJava
compileTestJava
test
jar
build
clean
```

You can think of a task as:

> **A unit of work that Gradle knows how to perform.**

For example:

```bash
gradle clean
```

means:

> Run the `clean` task.

And:

```bash
gradle test
```

means:

> Run the `test` task.

And:

```bash
gradle build
```

means:

> Perform the work required to build the project.

This task-based model will become very important later.

---

# 6. One important difference from Maven

With Maven, you learned about its lifecycle:

```text
validate
 ↓
compile
 ↓
test
 ↓
package
 ↓
verify
 ↓
install
 ↓
deploy
```

Gradle doesn't revolve around the same fixed lifecycle.

Instead, Gradle has a **task graph**.

For example:

```text
build
 ├── test
 │    ├── compileTestJava
 │    └── compileJava
 │
 └── jar
      └── compileJava
```

Gradle determines which tasks need to run based on their relationships.

We'll study this properly in a later lesson.

For now remember:

> **Maven is strongly lifecycle-oriented; Gradle is strongly task-oriented.**

---

# 7. The Gradle Wrapper

You'll encounter something important in real Gradle projects:

```text
gradlew
gradlew.bat
gradle/
```

These form the **Gradle Wrapper**.

Instead of requiring every developer to install the exact same Gradle version globally, the project can provide a wrapper that downloads/uses the project's specified Gradle version.

On Windows:

```powershell
.\gradlew.bat build
```

On Linux/macOS:

```bash
./gradlew build
```

This is extremely important in professional development because the project controls the Gradle version.

We'll spend an entire lesson on this.

---

For now, remember this:

```text
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
     Compile       Test       Package
        │           │           │
        ↓           ↓           ↓
      .class      Results       .jar
```

And:

```text

      │
      ↓
 tells Gradle
 how the project should be built
```

```kotlin
    useJUnitPlatform()
}
```

is also configuring Gradle's task model.

Later, you'll be able to write more sophisticated Gradle logic.

# Gradle — Lesson 6: Tasks & the Task Graph

**Goal:** Understand what Gradle tasks are, how to discover them, and how Gradle decides which tasks to run.

You already know:

> A Gradle task is a unit of work.

Now we're going to go one level deeper.

---

## 1. What Is a Gradle Task?

A task represents a specific piece of work Gradle can perform.

Examples from your project include:

```text
compileJava
compileTestJava
test
jar
build
run
clean
```

Think of a task as an instruction:

```text
compileJava → compile Java code
test        → run tests
jar         → create a JAR
clean       → remove build output
run         → run the application
```

---

# 2. Discover the Tasks

From your project directory:

```powershell
.\gradlew.bat tasks
```

Run that command.

Gradle will print a large list of available tasks.

You'll see categories such as:

```text
Application tasks
Build tasks
Build Setup tasks
Documentation tasks
Help tasks
Verification tasks
```

The exact output may vary depending on the Gradle version and plugins.

---

# 3. Why Are There So Many Tasks?

Remember this:

```kotlin
plugins {
    application
}
```

The Application Plugin adds functionality to the project.

That means it can also provide tasks.

Other plugins can add their own tasks too.

Conceptually:

```text
Gradle
  │
  ├── Java/Application plugin
  │       │
  │       ├── run
  │       ├── build
  │       ├── test
  │       ├── jar
  │       └── ...
  │
  └── Other plugins
          │
          └── additional tasks
```

So the task list isn't just a random collection of commands.

**Plugins contribute tasks to the project.**

---

# 4. Find a Specific Task

You can ask Gradle for information about a task.

Try:

```powershell
.\gradlew.bat help --task build
```

This asks Gradle:

> Tell me about the `build` task.

You can also inspect:

```powershell
.\gradlew.bat help --task test
```

and:

```powershell
.\gradlew.bat help --task run
```

This is an important developer habit:

> **When you don't know what a Gradle task does, ask Gradle.**

---

# 5. The `build` Task Isn't Doing Everything Itself

This is one of the most important concepts in this lesson.

When you execute:

```powershell
.\gradlew.bat build
```

you might imagine:

```text
build
 ↓
"build everything"
```

But Gradle actually uses **task dependencies**.

Conceptually:

```text
build
 │
 ├── check
 │    └── test
 │
 └── assemble
      └── jar
```

And those tasks may themselves depend on other tasks:

```text
test
 ↓
compileTestJava
 ↓
compileJava
```

The exact graph is more complicated, but the important idea is:

> **Tasks can depend on other tasks.**

---

# 6. Task Dependency

Imagine:

```text
A → B
```

This means:

> A depends on B.

Therefore, before Gradle can execute A, it needs B.

For example:

```text
test
 ↓
compileTestJava
```

means:

> The test code needs to be compiled before the tests can run.

So Gradle handles the order for you.

You don't manually run:

```powershell
.\gradlew.bat compileJava
.\gradlew.bat compileTestJava
.\gradlew.bat test
```

Instead:

```powershell
.\gradlew.bat test
```

Gradle determines what must happen first.

---

# 7. The Task Graph

This collection of task relationships is called the **task graph**.

Think of:

```text
               build
              /     \
             /       \
        assemble     check
           │           │
          jar         test
                       │
                compileTestJava
                       │
                  compileJava
```

This is simplified, but it gives you the right mental model.

Gradle looks at:

> "What did the user request?"

Then:

> "What tasks are required to accomplish that?"

Then:

> "What order do those tasks need to run in?"

---

# 8. Gradle Doesn't Necessarily Run Everything

Suppose you execute:

```powershell
.\gradlew.bat clean
```

Gradle doesn't need to compile Java.

It only needs to perform the work associated with `clean`.

Likewise:

```powershell
.\gradlew.bat test
```

doesn't necessarily require every task that `build` requires.

This is why tasks are useful:

```text
clean → clean build output
test  → run tests
jar   → create JAR
run   → run application
build → perform the broader build
```

---

# 9. The `clean` Task

Try:

```powershell
.\gradlew.bat clean
```

Then inspect:

```powershell
Get-ChildItem .\app\build
```

You should find that the build output has been removed.

Conceptually:

```text
Before:

app/build/
├── classes/
├── libs/
├── reports/
└── test-results/


clean

        ↓


After:

app/build/
    ↓
removed
```

`clean` is therefore useful when you want to remove generated build output.

---

# 10. Clean vs Build

You can combine tasks:

```powershell
.\gradlew.bat clean build
```

This means:

```text
1. clean
   ↓
2. build
```

So Gradle can receive multiple task requests.

This is common when you want a fresh build.

---

# 11. Project Tasks vs Subproject Tasks

Your project has:

```text
gradle-practice
└── app
```

Therefore, tasks can be addressed specifically to `app`.

For example:

```powershell
.\gradlew.bat :app:test
```

means:

```text
:
 ↓
root project
 ↓
app project
 ↓
test task
```

Compare:

```powershell
.\gradlew.bat test
```

with:

```powershell
.\gradlew.bat :app:test
```

In your current project, they effectively target the app's tests, but the explicit form becomes particularly useful when a build contains multiple subprojects.

---

# 12. Task Paths

This:

```text
:app:test
```

is called a **task path**.

The general structure is:

```text
:project:task
```

Your project:

```text
:app:test
```

means:

```text
project = app
task    = test
```

Later, with multiple projects:

```text
:backend:test
:frontend:test
:shared:build
```

can distinguish between tasks belonging to different projects.

---

# 13. Why This Matters in Real Projects

Imagine a professional application:

```text
company-system/
│
├── backend/
├── frontend/
├── database/
└── shared/
```

Each could potentially be a Gradle project.

You might have:

```text
:backend:build
:frontend:build
:shared:test
```

Without task paths, it would become difficult to identify exactly which project's task you're targeting.

---

# 14. Task Output

Run:

```powershell
.\gradlew.bat test
```

You'll see lines like:

```text
> Task :app:compileJava
> Task :app:compileTestJava
> Task :app:test
```

Notice the structure:

```text
:app:test
```

Again:

```text
:app:test
  │   │
  │   └── task
  │
  └── project
```

This is something you'll frequently see when working with Gradle.

---

# 15. A Useful Debugging Command

Gradle provides a very useful option:

```powershell
.\gradlew.bat build --dry-run
```

This tells Gradle:

> Show me which tasks would execute, but don't actually execute them.

This is useful for understanding the task graph.

For example, you might see:

```text
:app:compileJava SKIPPED
:app:compileTestJava SKIPPED
:app:test SKIPPED
:app:jar SKIPPED
:app:build SKIPPED

BUILD SUCCESSFUL
```

The important thing is:

**Gradle is showing the tasks it would execute without actually doing the work.**

---

# 16. Another Useful Command

Try:

```powershell
.\gradlew.bat build --dry-run
```

Then compare it with:

```powershell
.\gradlew.bat test --dry-run
```

You'll notice that the requested tasks produce different task graphs.

This is a great way to see that:

> `build` and `test` are not the same operation.

---

# 17. Task Graph Mental Model

Here's the key concept for this lesson:

```text
                 USER
                  │
                  │
                  ▼
          .\gradlew.bat build
                  │
                  ▼
            Gradle receives
             task request
                  │
                  ▼
             Task Graph
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
    compile    test       jar
        │         │
        │         ▼
        │    compileTestJava
        │
        ▼
   compileJava
```

Gradle figures out:

1. **Which tasks are required**
2. **Which tasks depend on others**
3. **What order they should run**
4. **Which tasks can be skipped because they're already up-to-date**

That's the heart of Gradle's task system.
