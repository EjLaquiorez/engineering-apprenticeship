# Lesson 1 — What Is Gradle?

Before touching commands, understand **why Gradle exists**.

Imagine a Java project containing:

```text
MyApp/
├── src/
│   ├── main/
│   │   └── java/
│   └── test/
│       └── java/
├── dependencies/
├── build/
└── ...
```

As the project grows, building it manually becomes annoying.

You would need to:

```text
find Java source files
        ↓
compile them
        ↓
find dependencies
        ↓
put dependencies on the classpath
        ↓
compile tests
        ↓
run tests
        ↓
package application
        ↓
produce JAR
```

A **build tool** automates this process.

Gradle is one of those build tools.

---

## 1. What does Gradle do?

At a high level:

> **Gradle automates the process of building, testing, and packaging software.**

For a Java project, Gradle can handle things such as:

* compiling Java code
* downloading dependencies
* compiling test code
* running tests
* creating JAR files
* cleaning generated files
* executing custom build tasks

Instead of manually doing:

```text
javac ...
java ...
```

you can eventually do:

```bash
./gradlew build
```

and Gradle coordinates the required work.

On Windows, you'll commonly use:

```powershell
.\gradlew.bat build
```

---

# 2. Why do we need a build tool?

You already learned Maven.

Maven solves this problem using a declarative configuration file:

```text
pom.xml
```

Gradle solves the same general problem, but uses Gradle build scripts.

A common Java Gradle project contains:

```text
build.gradle
```

or the Kotlin-based form:

```text
build.gradle.kts
```

For our apprenticeship, we'll initially focus on:

```text
build.gradle
```

because it uses the Groovy DSL and makes the fundamental Gradle concepts easier to see.

---

# 3. Gradle's job in our engineering model

Earlier we established this mental model:

```text
Computer
   ↓
Terminal / Shell
   ↓
Project files
   ↓
Git
   ↓
GitHub
   ↓
Build tool
   ↓
IDE
   ↓
Application
```

Gradle sits here:

```text
Java source code
      ↓
    Gradle
      ↓
 compile
      ↓
   test
      ↓
 package
      ↓
   JAR
```

So Gradle isn't Java itself.

It doesn't replace Java.

Instead:

```text
Java       → programming language
JDK        → tools/runtime for Java
Gradle     → build automation tool
JUnit      → testing framework
Git        → version control
GitHub     → remote collaboration platform
VS Code    → code editor
```

This distinction is important.

---

# 4. Maven vs Gradle

You just finished Maven, so this is a useful comparison.

### Maven

Configuration:

```text
pom.xml
```

Example dependency:

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>...</version>
</dependency>
```

### Gradle

Configuration:

```text
build.gradle
```

Dependency syntax is much shorter:

```groovy
dependencies {
    testImplementation 'org.junit.jupiter:junit-jupiter:...'
}
```

Both can accomplish things like:

```text
download dependencies
        ↓
compile
        ↓
test
        ↓
package
```

The major difference is **how you describe the build**.

Maven primarily uses XML configuration.

Gradle uses a build-script DSL.

---

# 5. Gradle is task-oriented

This is one of the most important concepts.

Gradle organizes work into **tasks**.

For example:

```text
compileJava
compileTestJava
test
jar
build
clean
```

You can think of a task as:

> **A unit of work that Gradle knows how to perform.**

For example:

```bash
gradle clean
```

means:

> Run the `clean` task.

And:

```bash
gradle test
```

means:

> Run the `test` task.

And:

```bash
gradle build
```

means:

> Perform the work required to build the project.

This task-based model will become very important later.

---

# 6. One important difference from Maven

With Maven, you learned about its lifecycle:

```text
validate
 ↓
compile
 ↓
test
 ↓
package
 ↓
verify
 ↓
install
 ↓
deploy
```

Gradle doesn't revolve around the same fixed lifecycle.

Instead, Gradle has a **task graph**.

For example:

```text
build
 ├── test
 │    ├── compileTestJava
 │    └── compileJava
 │
 └── jar
      └── compileJava
```

Gradle determines which tasks need to run based on their relationships.

We'll study this properly in a later lesson.

For now remember:

> **Maven is strongly lifecycle-oriented; Gradle is strongly task-oriented.**

---

# 7. The Gradle Wrapper

You'll encounter something important in real Gradle projects:

```text
gradlew
gradlew.bat
gradle/
```

These form the **Gradle Wrapper**.

Instead of requiring every developer to install the exact same Gradle version globally, the project can provide a wrapper that downloads/uses the project's specified Gradle version.

On Windows:

```powershell
.\gradlew.bat build
```

On Linux/macOS:

```bash
./gradlew build
```

This is extremely important in professional development because the project controls the Gradle version.

We'll spend an entire lesson on this.

---

For now, remember this:

```text
                 Gradle
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
     Compile       Test       Package
        │           │           │
        ↓           ↓           ↓
      .class      Results       .jar
```

And:

```text
build.gradle
      │
      ↓
 tells Gradle
 how the project should be built
```

# Gradle — Lesson 2: Installing and Verifying Gradle

Since you're on **Windows + VS Code**, we'll use **PowerShell** for this lesson.

## 1. Gradle Has Two Ways to Run

Before installing anything, understand these two commands:

### Global Gradle

```powershell
gradle
```

This uses a Gradle installation available on your system's `PATH`.

For example:

```text
Windows
   ↓
PATH
   ↓
Gradle installation
   ↓
gradle
```

### Gradle Wrapper

A project can instead contain:

```text
gradlew
gradlew.bat
gradle/
```

Then you run:

```powershell
.\gradlew.bat build
```

The project controls which Gradle version is used.

---

# 2. Why We Still Learn Global Gradle

You might wonder:

> "If the Wrapper is preferred, why install Gradle at all?"

Good question.

We want you to understand both.

The global installation lets you learn:

```powershell
gradle --version
```

and understand:

```text
Gradle
JVM
OS
architecture
```

However, when working with an actual project, you'll commonly see:

```powershell
.\gradlew.bat build
```

rather than:

```powershell
gradle build
```

Think of it like this:

```text
Global Gradle
    ↓
Machine-level tool

Gradle Wrapper
    ↓
Project-level tool
```

# 6. The Installation

For the actual installation, we'll use the official Gradle distribution rather than downloading some random third-party installer.

The current Gradle documentation provides installation instructions for Windows, including the required `PATH` configuration.

[Gradle Installation Documentation](https://docs.gradle.org/current/userguide/installation.html?utm_source=chatgpt.com)

```text
      ↓
Extract Gradle
      ↓

      ↓

      ↓

      ↓
gradle --version
```

### Important

Don't confuse:

```text

```

with:

```text
Gradle Wrapper
```

You are installing the **global Gradle command** here.

# 7. PATH

This should look familiar from our Terminal/Linux lessons.

When you type:

```powershell
gradle
```

Windows searches directories in your `PATH`.

Conceptually:

```text
gradle
  ↓
Search PATH directories
  ↓
Find gradle.bat / gradle executable
  ↓
Run Gradle
```

So if Gradle is installed at something like:

```text
C:\Gradle\gradle-x.x\
```

you generally add its:

```text
bin
```

directory to `PATH`:

```text
C:\Gradle\gradle-x.x\bin
```

Then Windows can find:

```text
gradle
```

from any directory.

---

# 8. Why Open a New Terminal?

After changing `PATH`, your **existing PowerShell session may not automatically receive the updated environment**.

Therefore:

```text
Old PowerShell
      ↓
old PATH

New PowerShell
      ↓
updated PATH
```

So after installation, close PowerShell and open a **new** PowerShell window.

Then:

```powershell
gradle --version
```

---

# 9. Verification

A successful installation should allow:

```powershell
gradle --version
```

to execute without a "not recognized" error.

Then check:

```powershell
where.exe gradle
```

This tells us where Windows found Gradle.

For example:

```text
C:\Gradle\gradle-x.x\bin\gradle.bat
```

That is useful because you're learning not just:

> "It works."

but also:

> "Where is the executable coming from?"

That's an important engineering habit.
