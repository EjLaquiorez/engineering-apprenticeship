# Lesson 1 — What Maven Is and Why It Exists

## 1. What is Maven?

Apache Maven is a **build automation and project management tool** commonly used for Java projects.

Maven automates tasks such as:

- Compiling Java source code
- Running tests
- Managing dependencies
- Packaging applications
- Managing project configuration
- Running build plugins

A simple mental model is:

```text
Project
   ↓
pom.xml
   ↓
Maven
   ↓
compile → test → package
   ↓
Application
```

---

## 2. Maven is not Java

Maven and Java have different responsibilities.

The **JDK** provides Java development tools such as `javac`.

For example:

```bash
javac Main.java
```

uses the Java compiler to compile a Java source file.

Maven is a higher-level build tool that can coordinate compilation, testing, dependency management, packaging, and other build activities.

### Mental model

```text
JDK
 ↓
Provides Java development tools

Maven
 ↓
Automates and coordinates the project build
```

---

## 3. What problem does Maven solve?

A small Java project can be compiled manually.

As a project grows, however, manual build management becomes difficult.

A real project may contain:

```text
50 Java source files
30 test classes
10 external libraries
multiple build steps
packaging requirements
multiple developers
```

Without a build tool, developers may have to manually:

1. Find required libraries.
2. Download the correct versions.
3. Configure the classpath.
4. Compile source code.
5. Compile tests.
6. Run tests.
7. Package the application.
8. Keep everyone's environment consistent.

Maven automates much of this process.

---

# 4. The `pom.xml` file

A Maven project has an important configuration file:

```text
pom.xml
```

POM means:

**Project Object Model**

The `pom.xml` describes the Maven project.

It can contain information such as:

- Project identity
- Project version
- Dependencies
- Java/compiler configuration
- Plugins
- Build configuration

Conceptually:

```text
my-project/
├── pom.xml
├── src/
│   ├── main/
│   └── test/
└── target/
```

The `pom.xml` tells Maven how the project is configured.

---

# 5. Maven and dependencies

Java applications often use external libraries.

For example:

```text
My Application
      ↓
   depends on
      ↓
External Library
```

Manually managing libraries can become difficult.

Maven allows dependencies to be declared in the project's `pom.xml`.

Maven can then resolve the required dependencies and make them available to the project.

This is one of Maven's major benefits.

---

# 6. Maven and convention

Maven follows the principle of:

**Convention over configuration**

Maven expects projects to follow a standard structure.

A typical Maven project uses:

```text
src/
├── main/
│   └── java/
│
└── test/
    └── java/
```

Because this structure is standardized, Maven already knows where to look for production code and test code.

Developers do not need to invent a completely different project layout for every project.

# 9. Key distinctions

## `javac`

`javac` is the Java compiler.

Example:

```bash
javac Main.java
```

Its primary job is compiling Java source code.

## Maven

Maven is a build automation and project management tool.

It can coordinate:

```text
Dependency resolution
       ↓
Compilation
       ↓
Testing
       ↓
Packaging
       ↓
Other build tasks
```

Therefore:

> `javac` is a compiler; Maven is a build tool that can orchestrate the overall Java build process.

---

# 10. Lesson 1 Summary

The important concepts from Lesson 1 are:

- Maven is a **build automation and project management tool**.
- Maven is commonly used for Java projects.
- Maven is **not the Java language** and is not the JDK.
- `javac` is the Java compiler.
- Maven can automate compilation, testing, dependency management, and packaging.
- `pom.xml` means **Project Object Model**.
- `pom.xml` describes and configures a Maven project.
- Maven uses a standard project structure.
- Maven follows **convention over configuration**.
- Maven helps make Java builds more consistent and repeatable.

# Lesson 2 — Maven Project Structure

Now we're going to get practical.

A Maven project normally looks like this:

```text
my-app/
│
├── pom.xml
│
└── src/
    ├── main/
    │   ├── java/
    │   └── resources/
    │
    └── test/
        ├── java/
        └── resources/
```

Before we create anything, I want you to understand **why each directory exists**.

### `pom.xml`

Maven's project configuration.

### `src/main/java`

Your application's production Java source code.

Example:

```text
src/main/java/
└── com/example/app/
    ├── Main.java
    ├── User.java
    └── UserService.java
```

### `src/main/resources`

Non-Java resources needed by the application.

Examples:

```text
application.properties
config files
templates
```

### `src/test/java`

Your Java test code.

Example:

```text
src/test/java/
└── com/example/app/
    └── UserServiceTest.java
```

### `src/test/resources`

Resources used by tests.

---

## One more directory: `target`

After Maven builds the project, you'll commonly see:

```text
target/
```

This contains generated build output.

For example:

```text
target/
├── classes/
├── test-classes/
└── my-app-1.0.jar
```

This is important because you've already learned about `.gitignore`.

Generally, **`target/` should not be committed to Git**.

Maven can recreate it from the source code and project configuration.

---

## The complete mental model

```text
my-app/
│
├── pom.xml                 ← Maven configuration
│
├── src/
│   ├── main/
│   │   ├── java/           ← application code
│   │   └── resources/      ← application resources
│   │
│   └── test/
│       ├── java/           ← test code
│       └── resources/      ← test resources
│
└── target/                 ← generated build output
```
