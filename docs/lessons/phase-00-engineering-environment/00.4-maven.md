# Lesson 1 — What Maven Is and Why It Exists

## 1. What is Maven?

Apache Maven is a **build automation and project management tool** commonly used for Java projects.

Maven automates tasks such as:

- Compiling Java source code
- Running tests
- Managing dependencies
- Packaging applications
- Managing project configuration
- Running build plugins

A simple mental model is:

```text
Project
   ↓
pom.xml
   ↓
Maven
   ↓
compile → test → package
   ↓
Application
```

---

## 2. Maven is not Java

Maven and Java have different responsibilities.

The **JDK** provides Java development tools such as `javac`.

For example:

```bash
javac Main.java
```

uses the Java compiler to compile a Java source file.

Maven is a higher-level build tool that can coordinate compilation, testing, dependency management, packaging, and other build activities.

### Mental model

```text
JDK
 ↓
Provides Java development tools

Maven
 ↓
Automates and coordinates the project build
```

---

## 3. What problem does Maven solve?

A small Java project can be compiled manually.

As a project grows, however, manual build management becomes difficult.

A real project may contain:

```text
50 Java source files
30 test classes
10 external libraries
multiple build steps
packaging requirements
multiple developers
```

Without a build tool, developers may have to manually:

1. Find required libraries.
2. Download the correct versions.
3. Configure the classpath.
4. Compile source code.
5. Compile tests.
6. Run tests.
7. Package the application.
8. Keep everyone's environment consistent.

Maven automates much of this process.

---

# 4. The `pom.xml` file

A Maven project has an important configuration file:

```text
pom.xml
```

POM means:

**Project Object Model**

The `pom.xml` describes the Maven project.

It can contain information such as:

- Project identity
- Project version
- Dependencies
- Java/compiler configuration
- Plugins
- Build configuration

Conceptually:

```text
my-project/
├── pom.xml
├── src/
│   ├── main/
│   └── test/
└── target/
```

The `pom.xml` tells Maven how the project is configured.

---

# 5. Maven and dependencies

Java applications often use external libraries.

For example:

```text
My Application
      ↓
   depends on
      ↓
External Library
```

Manually managing libraries can become difficult.

Maven allows dependencies to be declared in the project's `pom.xml`.

Maven can then resolve the required dependencies and make them available to the project.

This is one of Maven's major benefits.

---

# 6. Maven and convention

Maven follows the principle of:

**Convention over configuration**

Maven expects projects to follow a standard structure.

A typical Maven project uses:

```text
src/
├── main/
│   └── java/
│
└── test/
    └── java/
```

Because this structure is standardized, Maven already knows where to look for production code and test code.

Developers do not need to invent a completely different project layout for every project.

---

The engineering environment mental model is:

```text

   ↓

   ↓
Project Files
   ↓
Git
   ↓
GitHub
   ↓
```

```text
                 Maven
                   │
          ┌────────┴────────┐

      pom.xml           Commands

        └──────────┴──────────┘
```

The `pom.xml` describes the project.

Maven reads that configuration and performs the requested build operations.

---

# 9. Key distinctions

## `javac`

`javac` is the Java compiler.

Example:

```bash
javac Main.java
```

Its primary job is compiling Java source code.

## Maven

Maven is a build automation and project management tool.

It can coordinate:

```text
Dependency resolution
       ↓
Compilation
       ↓
Testing
       ↓
Packaging
       ↓
Other build tasks
```

Therefore:

> `javac` is a compiler; Maven is a build tool that can orchestrate the overall Java build process.

---

# 10. Lesson 1 Summary

The important concepts from Lesson 1 are:

- Maven is a **build automation and project management tool**.
- Maven is commonly used for Java projects.
- Maven is **not the Java language** and is not the JDK.
- `javac` is the Java compiler.
- Maven can automate compilation, testing, dependency management, and packaging.
- `pom.xml` means **Project Object Model**.
- `pom.xml` describes and configures a Maven project.
- Maven uses a standard project structure.
- Maven follows **convention over configuration**.
- Maven helps make Java builds more consistent and repeatable.

# Lesson 2 — Maven Project Structure

Now we're going to get practical.

A Maven project normally looks like this:

```text
my-app/
│
├── pom.xml
│
└── src/
    ├── main/
    │   ├── java/
    │   └── resources/
    │
    └── test/
        ├── java/
        └── resources/
```

Before we create anything, I want you to understand **why each directory exists**.

### `pom.xml`

Maven's project configuration.

### `src/main/java`

Your application's production Java source code.

Example:

```text
src/main/java/
└── com/example/app/
    ├── Main.java
    ├── User.java
    └── UserService.java
```

### `src/main/resources`

Non-Java resources needed by the application.

Examples:

```text
application.properties
config files
templates
```

### `src/test/java`

Your Java test code.

Example:

```text
src/test/java/
└── com/example/app/
    └── UserServiceTest.java
```

### `src/test/resources`

Resources used by tests.

---

## One more directory: `target`

After Maven builds the project, you'll commonly see:

```text
target/
```

This contains generated build output.

For example:

```text
target/
├── classes/
├── test-classes/
└── my-app-1.0.jar
```

This is important because you've already learned about `.gitignore`.

Generally, **`target/` should not be committed to Git**.

Maven can recreate it from the source code and project configuration.

---

## The complete mental model

```text
my-app/
│
├── pom.xml                 ← Maven configuration
│
├── src/
│   ├── main/
│   │   ├── java/           ← application code
│   │   └── resources/      ← application resources
│   │
│   └── test/
│       ├── java/           ← test code
│       └── resources/      ← test resources
│
└── target/                 ← generated build output
```

# Maven — Lesson 3: Understanding `pom.xml`

Now we're getting into one of the **most important parts of Maven**.

If Maven is the build tool, then `pom.xml` is essentially the **project's instruction/configuration file**.

---

## 1. What does POM mean?

`POM` stands for:

**Project Object Model**

The file is:

```text
pom.xml
```

It is an XML file that describes your Maven project.

Think of it like this:

```text
Maven
  ↑
  │ reads
  │
pom.xml
  │
  ├── Who is the project?
  ├── What version is it?
  ├── What does it depend on?
  ├── How should it be built?
  └── What plugins/configuration does it use?
```

---

# 2. A minimal `pom.xml`

A very small Maven project can have something like:

```xml
<project>
    <groupId>com.example</groupId>
    <artifactId>my-app</artifactId>
    <version>1.0-SNAPSHOT</version>
</project>
```

There are three important pieces here:

```text
groupId
artifactId
version
```

Together, these identify your Maven project.

We'll study each one carefully.

---

# 3. `groupId`

Example:

```xml
<groupId>com.example</groupId>
```

The `groupId` identifies the **organization, company, or group that owns the project**.

For example:

```text
com.google
org.apache
com.mycompany
```

A common convention is to use a reversed domain name.

If a company owns:

```text
example.com
```

it might use:

```text
com.example
```

If your organization were:

```text
mycompany.com
```

you might use:

```text
com.mycompany
```

For learning purposes, you'll often see:

```xml
<groupId>com.example</groupId>
```

---

# 4. `artifactId`

Example:

```xml
<artifactId>my-app</artifactId>
```

The `artifactId` identifies the **specific project/artifact**.

Think:

```text
groupId
    ↓
Who owns it?

artifactId
    ↓
Which project is it?
```

For example:

```xml
<groupId>com.example</groupId>
<artifactId>inventory-system</artifactId>
```

This means:

```text
Organization: com.example
Project:      inventory-system
```

---

# 5. `version`

Example:

```xml
<version>1.0-SNAPSHOT</version>
```

The version identifies the **version of your project**.

Examples:

```text
1.0
1.1
2.0
2.5.3
```

You may also see:

```text
1.0-SNAPSHOT
```

The word `SNAPSHOT` indicates that this is a development version rather than a finalized release.

We'll explore this more when we discuss Maven coordinates and repositories.

---

# 6. The three together

Suppose we have:

```xml
<groupId>com.example</groupId>
<artifactId>inventory-system</artifactId>
<version>1.0-SNAPSHOT</version>
```

We can think of it as:

```text
Who?
 ↓
com.example

What?
 ↓
inventory-system

Which version?
 ↓
1.0-SNAPSHOT
```

This combination is extremely important in Maven.

---

# 7. Maven coordinates

These three values form the core of what Maven calls **coordinates**:

```text
groupId
artifactId
version
```

For example:

```text
com.example:inventory-system:1.0-SNAPSHOT
```

You can think of this as the project's address in the Maven ecosystem.

We'll study Maven coordinates more deeply in **Lesson 4**.

For now, just remember:

```text
GAV
│ │ │
│ │ └── Version
│ └──── Artifact
└────── Group
```

**GAV = GroupId + ArtifactId + Version**

---

# 8. `packaging`

Another element you may see is:

```xml
<packaging>jar</packaging>
```

This tells Maven what type of artifact the project should produce.

For example:

```xml
<packaging>jar</packaging>
```

means the project produces a JAR.

Other packaging types exist, such as:

```text
jar
war
pom
```

For normal Java applications, you'll commonly encounter:

```xml
<packaging>jar</packaging>
```

An important detail:

If you don't specify `packaging`, Maven's default packaging is generally:

```text
jar
```

So this:

```xml
<packaging>jar</packaging>
```

is often unnecessary for a basic Java project.

---

# 9. Complete basic example

Putting the pieces together:

```xml
<project>
    <groupId>com.example</groupId>
    <artifactId>my-app</artifactId>
    <version>1.0-SNAPSHOT</version>
    <packaging>jar</packaging>
</project>
```

Conceptually:

```text
                 pom.xml
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
    groupId    artifactId     version
        │           │           │
     Who owns     Which       Which
     project?    project?     version?
        │           │           │
        └───────────┼───────────┘
                    ↓
             Maven coordinates
```

---

# 10. One important XML concept

You don't need to become an XML expert.

But you should understand the basic structure.

For example:

```xml
<artifactId>my-app</artifactId>
```

has:

```text
<artifactId>
    ↓
opening tag

my-app
    ↓
value

</artifactId>
    ↓
closing tag
```

So:

```xml
<version>1.0</version>
```

means the `version` element has the value:

```text
1.0
```

Maven reads these elements from the XML configuration.

---

# 11. Maven's actual POM root

In a real Maven `pom.xml`, you'll normally see a more complete root structure:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             https://maven.apache.org/xsd/maven-4.0.0.xsd">

    <modelVersion>4.0.0</modelVersion>

    <groupId>com.example</groupId>
    <artifactId>my-app</artifactId>
    <version>1.0-SNAPSHOT</version>

</project>
```

Don't worry about memorizing the namespace lines yet.

The important new element is:

```xml
<modelVersion>4.0.0</modelVersion>
```

This specifies the POM model version being used.

For now, remember the structure:

```text
project
 ├── modelVersion
 ├── groupId
 ├── artifactId
 └── version
```

---

# 12. Why is `pom.xml` so important?

Because as we continue through Maven, more functionality will be added to this file.

Eventually you will see something like:

```xml
<project>

    <modelVersion>4.0.0</modelVersion>

    <groupId>com.example</groupId>
    <artifactId>my-app</artifactId>
    <version>1.0-SNAPSHOT</version>

    <dependencies>
        ...
    </dependencies>

    <build>
        ...
    </build>

</project>
```

We'll learn these sections one at a time.

**Don't memorize the entire file.**

Understand what each section means.

# Lesson 4 — Maven Dependencies

This lesson answers one of the most important questions in real Java development:

> **How does my Java project use code written by someone else?**

For example, suppose your application needs a library for JSON processing.

You could download a `.jar` manually and put it somewhere in your project.

But professional Maven projects don't normally work that way.

Instead, you declare the dependency in `pom.xml`.

---

## 1. What is a dependency?

A **dependency** is software that your project needs in order to build or run.

Imagine your application:

```text
My Application
      │
      ├── needs JSON library
      │
      ├── needs database driver
      │
      └── needs testing library
```

Those external libraries are dependencies.

For example:

```text
Your Java application
        ↓
   Jackson library
        ↓
   JSON processing
```

Your application depends on Jackson.

---

# 2. Why Maven manages dependencies

Without Maven, you might have to:

```text
1. Find library
2. Download JAR
3. Put JAR somewhere
4. Configure classpath
5. Find library's dependencies
6. Download those too
7. Configure those
8. Repeat...
```

This becomes painful very quickly.

Maven automates much of this.

You tell Maven:

> "My project needs this library."

Maven determines what is needed and retrieves it from a repository.

---

# 3. Dependencies are declared in `pom.xml`

A Maven dependency looks like this:

```xml
<dependency>
    <groupId>...</groupId>
    <artifactId>...</artifactId>
    <version>...</version>
</dependency>
```

There are three important pieces:

```text
groupId
artifactId
version
```

Think of them as identifying a particular library.

---

# 4. `groupId`

The `groupId` identifies the organization or project that publishes the library.

For example:

```xml
<groupId>org.junit.jupiter</groupId>
```

This identifies the JUnit project/group.

You can think of it somewhat like a namespace:

```text
org.junit.jupiter
```

---

# 5. `artifactId`

The `artifactId` identifies the actual artifact/library.

For example:

```xml
<artifactId>junit-jupiter</artifactId>
```

Together:

```text
org.junit.jupiter
        +
junit-jupiter
```

identify the dependency.

---

# 6. `version`

Libraries have versions.

For example:

```xml
<version>...</version>
```

The version tells Maven **which version of the library your project should use**.

This matters because libraries change over time.

For example:

```text
Library
├── 1.0
├── 1.1
├── 2.0
└── 3.0
```

Your project shouldn't randomly receive a different version every time it builds.

You declare the version you want.

---

# 7. Putting it together

A dependency declaration has this structure:

```xml
<dependency>
    <groupId>org.example</groupId>
    <artifactId>some-library</artifactId>
    <version>1.0</version>
</dependency>
```

So Maven can identify:

```text
groupId
    ↓
WHO publishes it?

artifactId
    ↓
WHAT library is it?

version
    ↓
WHICH version?
```

---

# 8. Real example — JUnit

JUnit is commonly used for testing Java applications.

A dependency might look like:

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>...</version>
    <scope>test</scope>
</dependency>
```

Notice something new:

```xml
<scope>test</scope>
```

We'll discuss scopes shortly.

The important thing right now is that Maven knows:

```text
My project
    ↓
needs JUnit
    ↓
Maven retrieves JUnit
    ↓
my tests can use JUnit
```

---

# 9. Transitive dependencies

This is one of Maven's most powerful features.

Suppose:

```text
Your application
       ↓
Library A
       ↓
Library B
```

Your application directly depends on:

```text
Library A
```

But Library A itself requires:

```text
Library B
```

You don't necessarily have to manually declare Library B.

Maven can resolve the **transitive dependency**.

Conceptually:

```text
Your Application
      │
      ▼
  Library A
      │
      ▼
  Library B
```

Maven understands:

> "If the application needs A, and A needs B, B is also required."

This is one reason dependency management is so useful.

---

# 10. Where does Maven get dependencies?

Maven retrieves dependencies from **repositories**.

The basic flow is:

```text
pom.xml
   │
   │ dependency declaration
   ▼
Maven
   │
   ▼
Repository
   │
   ▼
JAR
   │
   ▼
Your project
```

There are different types of Maven repositories.

We'll study repositories properly in **Lesson 6**.

For now, remember:

> **A repository is where Maven can obtain project artifacts such as libraries.**

---

# 11. Local Maven repository

Remember this from Lesson 3:

```text
C:\Users\<username>\.m2\repository
```

That's your **local Maven repository**.

Once Maven downloads a dependency, it can store it there.

So the next time another Maven project needs the same dependency, Maven may already have it locally.

Conceptually:

```text
Internet repository
       ↓
     Maven
       ↓
.m2/repository
       ↓
    Project
```

This can make subsequent builds faster.

---

# 12. Dependency scope

A dependency can have a **scope**.

One important example is:

```xml
<scope>test</scope>
```

This means the dependency is intended for testing.

For example:

```text
Application code
       │
       X
      JUnit

Tests
       │
       ↓
     JUnit
```

JUnit is needed when running tests, but isn't normally something your production application needs at runtime.

Other scopes exist, including:

```text
compile
provided
runtime
test
system
import
```

You don't need to memorize all of them yet.

For this lesson, understand:

```text
compile → normal application dependency
test    → testing dependency
```

We'll go deeper when we reach testing.

---

# 13. Dependency vs plugin

This distinction is extremely important.

A **dependency** provides code that your application uses.

A **plugin** performs build-related work.

Think:

```text
DEPENDENCY
    ↓
Provides functionality
    ↓
Your application uses it


PLUGIN
    ↓
Performs build operation
    ↓
Maven uses it
```

For example:

```text
JUnit
    ↓
dependency
    ↓
used by your tests
```

Whereas:

```text
Maven Compiler Plugin
    ↓
plugin
    ↓
```

# Lesson 5 — Maven Plugins

Now we're going to answer an important question:

> **If a Maven lifecycle says `compile`, `test`, or `package`, what actually performs those operations?**

The answer is:

> **Maven plugins.**

---

## 1. What is a Maven plugin?

A Maven **plugin is a component that performs a specific build-related task**.

For example:

```text
Maven
  │
  ├── compile Java
  ├── run tests
  ├── package application
  └── generate reports
```

Plugins provide the functionality that allows Maven to perform those operations.

Think of it this way:

```text
Lifecycle
    ↓
"What stage should Maven perform?"

Plugin
    ↓
"How should Maven perform that work?"
```

This distinction is important.

---

# 2. Dependency vs plugin

You already learned this in Lesson 4.

Let's reinforce it.

### Dependency

A dependency provides functionality **to your application**.

```text
Your application
       ↓
uses
       ↓
Library
```

Example:

```text
JUnit
```

Your test code uses JUnit.

---

### Plugin

A plugin provides functionality **to Maven's build process**.

```text
Maven
  ↓
uses
  ↓
Plugin
  ↓
performs build operation
```

For example:

```text
Maven Compiler Plugin
        ↓
compiles Java source
```

So:

```text
Dependency → your application uses it

Plugin     → Maven uses it
```

Keep that distinction.

---

# 3. The Maven Compiler Plugin

When you run:

```powershell
mvn compile
```

Maven needs something that knows how to compile Java source code.

That's where the **Maven Compiler Plugin** comes in.

Conceptually:

```text
mvn compile
     ↓
compile phase
     ↓
Compiler Plugin
     ↓
javac
     ↓
.class files
```

Your source:

```text
src/main/java/App.java
```

gets compiled into something like:

```text
target/classes/App.class
```

The plugin is responsible for the compilation operation.

---

# 4. Plugin coordinates

Plugins also have identifying information.

You'll often see something like:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <version>...</version>
</plugin>
```

Notice that this looks similar to a dependency:

```xml
<groupId>...</groupId>
<artifactId>...</artifactId>
<version>...</version>
```

That's because plugins are themselves Maven artifacts.

But their **purpose is different**.

```text
Dependency
→ library your application uses

Plugin
→ tool Maven uses during the build
```

---

# 5. Plugins and lifecycle phases

This is where Lesson 3 and Lesson 5 connect.

You learned:

```text
validate
   ↓
compile
   ↓
test
   ↓
package
```

Now add plugins:

```text
compile
   ↓
Compiler Plugin
   ↓
compile Java


test
   ↓
Surefire Plugin
   ↓
run tests


package
   ↓
Packaging-related plugin
   ↓
create artifact
```

So a lifecycle phase can have plugin goals bound to it.

---

# 6. Plugin goals

A plugin contains **goals**.

A goal represents a specific operation that the plugin can perform.

Think:

```text
Plugin
   │
   ├── Goal A
   ├── Goal B
   └── Goal C
```

For example, the compiler plugin has a goal commonly called:

```text
compile
```

So conceptually:

```text
maven-compiler-plugin
        │
        └── compile goal
                 ↓
             compile Java
```

This gives us another important vocabulary:

```text
Lifecycle
    ↓
Phase
    ↓
Plugin
    ↓
Goal
```

---

# 7. Phase vs goal

This can initially be confusing.

### Phase

A **phase** belongs to a Maven lifecycle.

Examples:

```text
compile
test
package
install
```

### Goal

A **goal** belongs to a plugin.

Examples conceptually:

```text
compiler plugin
    ↓
compile goal

surefire plugin
    ↓
test goal
```

A useful mental model:

```text
PHASE
"What stage of the build are we in?"

GOAL
"What specific operation should a plugin perform?"
```

---

# 8. Plugin execution

When you run:

```powershell
mvn compile
```

you are requesting a **lifecycle phase**.

Maven then determines which plugin goals are associated with that phase.

Conceptually:

```text
mvn compile
     ↓
compile phase
     ↓
compiler plugin
     ↓
compile goal
     ↓
Java compilation
```

This is happening behind the scenes.

That's why you don't normally need to manually invoke the compiler plugin every time.

---

# 9. Plugins can be configured in `pom.xml`

Sometimes the default Maven behavior isn't enough.

You can configure a plugin.

For example:

```xml
<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>...</version>
            <configuration>
                ...
            </configuration>
        </plugin>
    </plugins>
</build>
```

The important structure is:

```text
build
  ↓
plugins
  ↓
plugin
  ↓
configuration
```

We'll eventually use this to configure things such as the Java version.

---

# 10. Why plugins matter

Imagine your project requires:

```text
Java 21
```

You want Maven to compile your project correctly for that Java version.

You can configure Maven's compiler behavior.

Conceptually:

```text
pom.xml
   ↓
compiler plugin configuration
   ↓
Java compilation settings
   ↓
compiled application
```

This is much better than relying on everyone manually remembering compiler settings.

---

# 11. Maven's default behavior

An important beginner misconception is:

> "I need to put every Maven plugin inside my `pom.xml`."

**Not necessarily.**

Maven has default plugin bindings for common lifecycle phases.

That's why a basic Maven project can often run:

```powershell
mvn compile
```

without you explicitly adding a compiler plugin configuration.

Maven already knows how common Java builds should work.

You add/configure plugins when you need to change or extend that behavior.

---

# 12. Example: running tests

Earlier we learned:

```powershell
mvn test
```

Now we can understand it at a deeper level.

Conceptually:

```text
mvn test
   ↓
test lifecycle phase
   ↓
test-related plugin execution
   ↓
tests run
```

One commonly used Maven plugin for executing tests is the **Maven Surefire Plugin**.

So:

```text
Surefire Plugin
       ↓
executes tests
```

Again:

> The lifecycle tells Maven **when**; the plugin provides the **operation**.

This is the model I want you to build:

# Lesson 6 — Maven Repositories

We've learned that your project can declare a dependency:

```xml
<dependency>
    <groupId>...</groupId>
    <artifactId>...</artifactId>
    <version>...</version>
</dependency>
```

But there's an obvious question:

> **Where does Maven get that dependency from?**

That's what repositories are about.

---

# 1. What is a Maven repository?

A **Maven repository is a location where Maven artifacts are stored**.

An artifact can be something like:

```text
JAR
POM
plugin
```

For example:

```text
Jackson library
JUnit
Maven Compiler Plugin
```

can all be represented as Maven artifacts.

Think of a repository as a **warehouse of Java libraries and build components**.

```text
             Maven Repository
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
      JUnit      Jackson      Other
      JAR         JAR        libraries
```

---

# 2. Three repository types

There are three important repository concepts:

```text
1. Local repository
2. Central repository
3. Remote repository
```

Let's examine them.

---

# 3. Local repository

You encountered this in Lesson 3.

On Windows, Maven normally stores its local repository here:

```text
C:\Users\<username>\.m2\repository
```

For you, this is conceptually:

```text
C:\Users\ejlqr\.m2\repository
```

The local repository is on **your own computer**.

It acts as a cache/storage location for Maven artifacts.

---

# 4. Why does Maven have a local repository?

Imagine you have two projects:

```text
Project A
    ↓
needs JUnit

Project B
    ↓
needs JUnit
```

The first time Maven needs JUnit:

```text
Internet repository
       ↓
     Maven
       ↓
.m2/repository
```

Maven downloads it.

Later:

```text
Project B
    ↓
Maven
    ↓
.m2/repository
    ↓
JUnit already available
```

Maven can reuse the locally stored artifact rather than downloading it again.

So `.m2/repository` serves an important caching role.

---

# 5. Central repository

One of the most important Maven repositories is **Maven Central**.

It is a large public repository containing Java libraries and other Maven artifacts.

Conceptually:

```text
             Maven Central
                   │
       ┌───────────┼───────────┐
       ↓           ↓           ↓
     JUnit       Jackson      etc.
```

When your project declares a dependency that isn't already available locally, Maven can retrieve it from configured remote repositories such as Maven Central.

---

# 6. The dependency flow

Now connect what we've learned in Lessons 4 and 6:

```text
pom.xml
   │
   │ dependency
   ▼
Maven
   │
   │ search locally
   ▼
.m2/repository
   │
   │ not found?
   ▼
Remote repository
   │
   ▼
Download artifact
   │
   ▼
.m2/repository
   │
   ▼
Your Maven build
```

This is an extremely important Maven workflow.

---

# 7. What is an artifact?

You've heard this word several times.

An **artifact** is a file produced or consumed by Maven that is identified by Maven coordinates.

For example:

```text
my-app-1.0-SNAPSHOT.jar
```

can be an artifact produced by your project.

A dependency such as JUnit can also be represented by an artifact.

So:

```text
Your project
    ↓
produces
    ↓
JAR artifact
```

while:

```text
Your project
    ↓
needs
    ↓
JUnit artifact
```

---

# 8. Maven coordinates

Remember:

```xml
<groupId>org.junit.jupiter</groupId>
<artifactId>junit-jupiter</artifactId>
<version>...</version>
```

These are called **Maven coordinates**.

The coordinates identify an artifact.

Think:

```text
groupId
   +
artifactId
   +
version
   =
specific artifact
```

For example:

```text
org.junit.jupiter
        +
junit-jupiter
        +
version
        ↓
specific JUnit artifact
```

This is how Maven knows exactly what you're asking for.

---

# 9. Repository directory structure

The local repository organizes artifacts according to their coordinates.

Conceptually:

```text
.m2/
└── repository/
    └── org/
        └── junit/
            └── jupiter/
                └── ...
```

The exact structure gets more detailed as you go deeper, but the important idea is:

```text
groupId
   ↓
directory structure

artifactId
   ↓
artifact directory

version
   ↓
version directory
```

So Maven can organize thousands of artifacts systematically.

---

# 10. Local vs remote

This distinction is important.

### Local repository

Located on your computer:

```text
~/.m2/repository
```

On Windows:

```text
C:\Users\<username>\.m2\repository
```

### Remote repository

Located somewhere accessible over a network.

For example:

```text
Maven Central
```

Conceptually:

```text
LOCAL

Your computer
└── .m2/repository


REMOTE

Internet
└── Maven Central
```

---

# 11. Why isn't `.m2` inside your project?

You might wonder:

> Why doesn't Maven put downloaded libraries inside my project directory?

Because the same dependency can be used by many projects.

Imagine:

```text
Project A ──┐
            │
Project B ──┼──→ .m2/repository
            │
Project C ──┘
```

They can share the locally cached artifacts.

Your project therefore doesn't normally need to contain every external JAR.

---

# 12. What happens if you delete `.m2/repository`?

This is a useful thought experiment.

Suppose you remove your local Maven repository.

Your project still has:

```text
pom.xml
```

and:

```text
<dependency>
    ...
</dependency>
```

But the downloaded dependency isn't locally available anymore.

When Maven builds the project, it can retrieve the required artifact from a remote repository again.

Conceptually:

```text
.m2/repository
     ↓
deleted
     ↓
mvn package
     ↓
Maven needs dependency
     ↓
remote repository
     ↓
download again
     ↓
.m2/repository
```

This is why deleting `.m2` can cause a subsequent build to download many dependencies again.

---

# 13. Repository vs dependency

Don't confuse these:

```text
Dependency
    ↓
Something your project needs

Repository
    ↓
Where Maven gets/stores artifacts
```

For example:

```text
Your project
     │
     │ needs
     ▼
   JUnit
     │
     │ retrieved from
     ▼
Maven Central
     │
     │ cached in
     ▼
.m2/repository
```

---

# 14. Repository vs plugin

We've now discussed three different things:

```text
Dependency
Plugin
Repository
```

They have different jobs.

| Concept    | Purpose                                 |
| ---------- | --------------------------------------- |
| Dependency | Library your application/test code uses |
| Plugin     | Performs Maven build operations         |
| Repository | Stores/provides Maven artifacts         |

For example:

```text
                  Repository
                 /          \
                /            \
               ↓              ↓
          JUnit artifact   Compiler Plugin
               ↓              ↓
          Dependency        Plugin
               ↓              ↓
          Your tests       Maven build
```

---

# 15. A complete Maven picture

At this point, your mental model should look like this:

```text
                         pom.xml
                            │
             ┌──────────────┴──────────────┐
             │                             │
        dependencies                    build/plugins
             │                             │
             ▼                             ▼
          JUnit                    Compiler Plugin
             │                             │
             └──────────────┬──────────────┘
                            │
                           Maven
                            │
                            ▼
                     Repository system
                      /             \
                     /               \
                    ▼                 ▼
             Local repository    Remote repository
                .m2/             Maven Central
                    │                 │
                    └───────┬─────────┘
                            ▼
                       Maven build
```

---

# 16. Important distinction: Central vs local

Don't think:

> "Maven Central is where Maven always gets everything."

The actual workflow is closer to:

```text
Does local repository have it?
          │
      ┌───┴───┐
     YES      NO
      │        │
      ▼        ▼
    use     remote repository
               │
               ▼
            download
               │
               ▼
        local repository
```

That's why Maven can become faster after the first build.

# Lesson 7 — Maven Testing

Now we're going to connect several things you've already learned:

```text
Maven lifecycle
      ↓
test phase
      ↓
test plugin
      ↓
JUnit tests
      ↓
BUILD SUCCESS / BUILD FAILURE
```

The goal isn't just to learn `mvn test`.

You need to understand **how Maven finds, compiles, and runs your tests**.

---

# 1. Why do we test?

Suppose you have a Java class:

```java id="7zn2cx"
public class Calculator {

    public int add(int a, int b) {
        return a + b;
    }
}
```

You expect:

```text id="v5e5ro"
add(2, 3)
    ↓
5
```

You could manually run the application and check the result.

But as applications become larger, manually checking everything becomes impractical.

Instead, we write automated tests:

```text id="q3ob9t"
Calculator
    ↓
automated tests
    ↓
verify behavior
```

Then Maven can execute those tests for us.

---

# 2. Main code vs test code

Remember the Maven project structure from Lesson 2:

```text id="9v4d2e"
my-app/
│
├── pom.xml
│
└── src/
    ├── main/
    │   ├── java/
    │   └── resources/
    │
    └── test/
        ├── java/
        └── resources/
```

The important distinction is:

```text id="s1yd81"
src/main/java
    ↓
production/application code


src/test/java
    ↓
test code
```

For example:

```text id="5mg5xk"
src/
├── main/
│   └── java/
│       └── Calculator.java
│
└── test/
    └── java/
        └── CalculatorTest.java
```

---

# 3. What is JUnit?

**JUnit** is a testing framework for Java.

Your Java code:

```text id="q9g7pg"
Calculator.java
```

can be tested using:

```text id="bbt4p9"
CalculatorTest.java
```

JUnit provides tools that allow you to write assertions such as:

```java id="y9v6h1"
assertEquals(5, calculator.add(2, 3));
```

This means:

> "I expect the result to be 5."

If the actual result is 5:

```text id="w0dyc7"
PASS
```

If the actual result is something else:

```text id="q8f2c7"
FAIL
```

---

# 4. JUnit is a dependency

This connects directly to Lesson 4.

JUnit isn't built into your application.

Your test code needs it.

Therefore, JUnit is declared as a Maven dependency.

Conceptually:

```text id="5y1yr8"
pom.xml
   │
   ▼
JUnit dependency
   │
   ▼
src/test/java
   │
   ▼
JUnit tests
```

A typical dependency looks like:

```xml id="m0c9dt"
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>...</version>
    <scope>test</scope>
</dependency>
```

Notice:

```xml id="9x1lkh"
<scope>test</scope>
```

You learned this in Lesson 4.

JUnit is intended for testing rather than being a normal production dependency.

---

# 5. Writing a test

A simple JUnit test might look like:

```java id="g6t1qf"
import static org.junit.jupiter.api.Assertions.assertEquals;

import org.junit.jupiter.api.Test;

public class CalculatorTest {

    @Test
    void additionWorks() {
        Calculator calculator = new Calculator();

        assertEquals(5, calculator.add(2, 3));
    }
}
```

Don't worry about understanding every part of this Java code yet.

The important pieces for Maven are:

```java id="f0r0dn"
@Test
```

and:

```java id="r9ry6h"
assertEquals(...)
```

`@Test` tells JUnit:

> "This method is a test."

`assertEquals` checks whether the actual result matches the expected result.

---

# 6. How Maven runs tests

You already learned that:

```bash id="3f2r4c"
mvn test
```

runs the Maven `test` phase.

Now we can see what happens underneath:

```text id="jq83qp"
mvn test
    ↓
test phase
    ↓
compile main code
    ↓
compile test code
    ↓
test plugin
    ↓
JUnit tests execute
    ↓
test results
```

This connects Lessons 3, 4, and 5.

Conceptually:

# Lesson 8 — Maven Packaging and JARs

We've already used:

```bash
mvn package
```

But what exactly happens when Maven packages your application?

And what is a **JAR**?

That's what we're going to learn.

---

## 1. What is packaging?

**Packaging is the process of taking your compiled application and producing a distributable artifact.**

For a typical Java application:

```text
Java source
    ↓
compile
    ↓
.class files
    ↓
package
    ↓
JAR
```

For example:

```text
src/main/java/App.java
        ↓
    compilation
        ↓
target/classes/App.class
        ↓
    packaging
        ↓
target/my-app-1.0-SNAPSHOT.jar
```

---

# 2. What is a JAR?

**JAR** stands for:

> **Java ARchive**

A JAR is an archive file used to package Java classes and related resources.

It normally has the extension:

```text
.jar
```

For example:

```text
my-app-1.0-SNAPSHOT.jar
```

You can think of it as a container:

```text
my-app.jar
├── Java classes
├── resources
└── metadata
```

Instead of distributing hundreds of individual `.class` files, you can package them into one JAR.

---

# 3. Before packaging

Suppose your project contains:

```text
src/
└── main/
    └── java/
        └── App.java
```

After:

```bash
mvn compile
```

you may have:

```text
target/
└── classes/
    └── App.class
```

The `.class` file is compiled Java bytecode.

But you don't necessarily want to distribute your project as:

```text
App.class
OtherClass.class
AnotherClass.class
...
```

Instead, Maven can package those files.

---

# 4. `mvn package`

Run:

```bash
mvn package
```

Maven goes through the necessary lifecycle phases:

```text
validate
   ↓
compile
   ↓
test
   ↓
package
```

At the package phase, Maven creates the configured artifact.

For a JAR project:

```text
target/
└── my-app-1.0-SNAPSHOT.jar
```

---

# 5. Where does the JAR go?

Maven normally puts build output inside:

```text
target/
```

So you might see:

```text
target/
├── classes/
├── test-classes/
├── surefire-reports/
└── my-app-1.0-SNAPSHOT.jar
```

The important one for this lesson is:

```text
target/my-app-1.0-SNAPSHOT.jar
```

---

# 6. Packaging type

Maven projects have a **packaging type**.

In `pom.xml`, you may see:

```xml
<packaging>jar</packaging>
```

For example:

```xml
<project>
    <modelVersion>4.0.0</modelVersion>

    <groupId>com.example</groupId>
    <artifactId>my-app</artifactId>
    <version>1.0-SNAPSHOT</version>

    <packaging>jar</packaging>
</project>
```

This tells Maven what kind of artifact the project produces.

---

# 7. What if `<packaging>` isn't specified?

This is an important Maven convention.

If you don't specify:

```xml
<packaging>
```

the default packaging type is:

```text
jar
```

So this:

```xml
<artifactId>my-app</artifactId>
<version>1.0-SNAPSHOT</version>
```

normally produces a JAR unless you configure something else.

This is another example of Maven's convention-over-configuration philosophy.

---

# 8. Other packaging types

You don't always create JARs.

Common packaging types include:

```text
jar
war
pom
```

### JAR

Common for:

```text
Java libraries
Java applications
```

Produces:

```text
something.jar
```

### WAR

WAR stands for:

> **Web Application Archive**

Used for certain Java web applications.

Produces:

```text
something.war
```

### POM

A project can also have:

```xml
<packaging>pom</packaging>
```

This is commonly used for parent or aggregation projects.

For now, your main focus is:

```text
JAR
```

---

# 9. Artifact coordinates

Remember Lesson 6.

Your project has:

```text
groupId
artifactId
version
```

For example:

```xml
<groupId>com.example</groupId>
<artifactId>my-app</artifactId>
<version>1.0</version>
```

Maven can produce:

```text
my-app-1.0.jar
```

Notice how the artifact name contains:

```text
artifactId
    +
version
```

Conceptually:

```text
my-app-1.0.jar
   │     │
   │     └── version
   └──────── artifactId
```

---

# 10. `SNAPSHOT`

You've probably seen:

```text
1.0-SNAPSHOT
```

For example:

```text
my-app-1.0-SNAPSHOT.jar
```

`SNAPSHOT` indicates that the version represents a development version rather than a finalized release.

Think:

```text
1.0-SNAPSHOT
    ↓
development version

1.0
    ↓
release version
```

Don't overthink the details yet—we'll encounter versioning more as we work with Maven repositories.

---

# 11. JAR contents

A JAR is essentially an archive.

You can inspect one using tools such as:

```bash
jar tf my-app.jar
```

The `t` means list the archive's contents and `f` specifies the JAR file.

You might see:

```text
META-INF/
META-INF/MANIFEST.MF
App.class
```

If your project has packages:

```text
META-INF/
META-INF/MANIFEST.MF
com/
com/example/
com/example/App.class
```

So:

```text
JAR
 ↓
contains compiled classes/resources
```

---

# 12. JAR vs `.class`

This distinction is important.

A `.class` file:

```text
App.class
```

contains compiled Java bytecode for a class.

A JAR:

```text
my-app.jar
```

can contain:

```text
App.class
User.class
Database.class
resources
metadata
...
```

So:

```text
.class
   ↓
one compiled class

.jar
   ↓
archive containing classes/resources
```

---

# 13. Packaging doesn't automatically mean "executable"

This is a very important beginner concept.

You might think:

> "If Maven created a JAR, I can automatically run it with `java -jar`."

**Not necessarily.**

A JAR can simply be a library/archive.

For example:

```text
library.jar
```

might contain useful classes that another application uses.

To make a JAR directly executable with:

```bash
java -jar my-app.jar
```

the JAR needs the appropriate metadata/configuration, such as a `Main-Class` entry in its manifest, and any required runtime dependencies must also be handled.

We'll explore executable JARs later.

---

# 14. Library JAR vs application JAR

Consider two scenarios.

### Library

```text
my-library.jar
```

Another application uses it:

```text
Application
    ↓
my-library.jar
```

The JAR doesn't necessarily run by itself.

### Application

```text
my-app.jar
```

Potentially:

```bash
java -jar my-app.jar
```

This requires the JAR to be configured appropriately.

So:

> **JAR means packaged Java artifact; it does not automatically mean executable application.**

---

# 15. `package` vs `install`

This connects back to Lesson 3.

### `mvn package`

Creates the artifact:

```text
mvn package
     ↓
target/my-app.jar
```

### `mvn install`

Goes further:

```text
mvn install
     ↓
package
     ↓
JAR
     ↓
install into local Maven repository
```

So:

```text
package
    ↓
creates artifact

install
    ↓
creates artifact
    +
puts it into local repository
```

---

Now you can see the entire Maven process we've learned so far:

```text
                    pom.xml
                       │
                       ▼
                    Maven
                       │
                       ▼
                   Lifecycle
                       │
                       ▼
                     Phase
                       │
                       ▼
                    Plugin
                       │
                       ▼
                      Goal
                       │
                       ▼
                 Java compilation
                       │
                       ▼
                   .class files
                       │
                       ▼
                    package
                       │
                       ▼
                     JAR
                       │
                 ┌─────┴─────┐
                 ▼           ▼
             package       install
                 │           │
                 ▼           ▼
             target/       .m2/
               JAR       repository
```

That's a much more complete understanding of Maven than simply knowing:

```bash
mvn package
```
