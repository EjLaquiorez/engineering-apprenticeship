# Lesson 23 — Method Design

So far, we've learned **how methods work**.

Now we need to learn something more important:

> **How do I decide what a method should do?**

Knowing the syntax isn't enough.

A developer needs to look at a problem and decide:

* Should this logic be a method?
* What should I call the method?
* What inputs does it need?
* Should it return something?
* Should it be `void`?
* Is the method doing too much?

---

# 1. Single Responsibility

A good method should generally have **one clear responsibility**.

For example:

```java
static void displayWelcome() {
    System.out.println("Welcome!");
}
```

Its responsibility is obvious:

> Display the welcome message.

Another:

```java
static int calculateTotal(int price, int quantity) {
    return price * quantity;
}
```

Its responsibility is:

> Calculate a total.

That's good method design.

---

## What about this?

```java
static void processOrder() {
    System.out.println("Welcome to the store.");

    int price = 100;
    int quantity = 3;

    int total = price * quantity;

    System.out.println("Total: " + total);

    if (total > 200) {
        System.out.println("You qualify for a discount.");
    }

    System.out.println("Thank you for your order.");
}
```

This method works.

But it is responsible for several things:

```text
processOrder()
│
├── Display welcome
├── Calculate total
├── Display total
├── Check discount
└── Display goodbye
```

That's becoming a **large responsibility**.

We could separate it:

```java
static void displayWelcome() {
    System.out.println("Welcome to the store.");
}

static int calculateTotal(int price, int quantity) {
    return price * quantity;
}

static boolean qualifiesForDiscount(int total) {
    return total > 200;
}

static void displayGoodbye() {
    System.out.println("Thank you for your order.");
}
```

Now each method has a clearer responsibility.

---

# 2. Method Naming

A method name should tell you **what the method does**.

Good:

```java
calculateTotal()
displayMenu()
getScore()
checkAge()
printReceipt()
```

Poor:

```java
doStuff()
thing()
method1()
process()
x()
```

When you see:

```java
calculateTotal(100, 3);
```

you should have a reasonable idea of what it does **without opening the method**.

---

# 3. Inputs and Outputs

A very useful way to design a method is to think:

```text
INPUT → METHOD → OUTPUT
```

For example:

```java
static int calculateTotal(int price, int quantity) {
    return price * quantity;
}
```

Think:

```text
price ──────┐
            ↓
        calculateTotal()
            ↓
quantity ───┘
            ↓
          total
```

So:

* **Inputs:** `price`, `quantity`
* **Processing:** multiplication
* **Output:** `int`

---

Another example:

```java
static void displayName(String name) {
    System.out.println("Name: " + name);
}
```

Think:

```text
name
 ↓
displayName()
 ↓
prints something
```

* **Input:** `name`
* **Processing:** formatting/printing
* **Output:** none → `void`

---

# 4. Deciding Between `void` and a Return Value

Ask:

> **Does the caller need a value from this method?**

### No → `void`

```java
static void displayMenu() {
    System.out.println("1. Start");
    System.out.println("2. Exit");
}
```

The method performs an action.

The caller doesn't need a value from it.

### Yes → return a value

```java
static int calculateTotal(int price, int quantity) {
    return price * quantity;
}
```

The caller needs the calculated total.

---

# 5. Avoid Unnecessarily Large Methods

Imagine this:

```java
static void runProgram() {
    // 50 lines displaying menus

    // 30 lines getting user input

    // 40 lines calculating data

    // 30 lines validating input

    // 50 lines displaying results
}
```

It may work, but it's difficult to understand and maintain.

Instead:

```java
static void runProgram() {
    displayMenu();
    getInput();
    calculateData();
    validateData();
    displayResults();
}
```

Now `runProgram()` becomes an **orchestrator**.

It tells us the overall flow without forcing us to read every implementation detail.

This is one of the major benefits of methods:

> **Methods allow us to organize complexity.**
