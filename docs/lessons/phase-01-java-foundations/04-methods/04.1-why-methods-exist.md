# Topic 4 — Methods

## Lesson 17 — Why Methods Exist

### What we're learning

Methods are not just another piece of Java syntax.

The goal of this lesson is to understand **why we need methods in the first place**.

We'll focus on three ideas:

1. **Breaking programs into responsibilities**
2. **Reusing logic**
3. **Method boundaries**

Before we touch method syntax, I want you to understand the problem methods are designed to solve.

---

## 1. The Problem: One Giant `main`

Imagine we are building a simple calculator:

```java
public class Calculator {

    public static void main(String[] args) {

        int firstNumber = 10;
        int secondNumber = 5;

        int sum = firstNumber + secondNumber;
        System.out.println("Sum: " + sum);

        int difference = firstNumber - secondNumber;
        System.out.println("Difference: " + difference);

        int product = firstNumber * secondNumber;
        System.out.println("Product: " + product);

        int quotient = firstNumber / secondNumber;
        System.out.println("Quotient: " + quotient);
    }
}
```

This program works.

But imagine the program grows:

```text
main()
 ├── get user input
 ├── validate input
 ├── calculate addition
 ├── calculate subtraction
 ├── calculate multiplication
 ├── calculate division
 ├── display results
 ├── handle errors
 └── repeat menu
```

Eventually, `main()` becomes responsible for **everything**.

That's the problem methods help us solve.

---

# 2. Breaking a Program Into Responsibilities

Instead of one giant block:

```text
main()
    ↓
do everything
```

we can conceptually divide the program:

```text
main()
 ├── get input
 ├── calculate
 └── display result
```

Each part can eventually become its own method:

```text
main()
 ├── getInput()
 ├── calculate()
 └── displayResult()
```

Now each method has a **responsibility**.

For example:

```text
getInput()
    → responsible for getting input

calculate()
    → responsible for calculation

displayResult()
    → responsible for displaying output
```

This is one of the most important ideas in this topic:

> **A method should represent a specific responsibility.**

We're not worrying about the exact syntax yet.

---

# 3. Reusing Logic

Consider this:

```java
int result1 = 10 + 5;
int result2 = 20 + 30;
int result3 = 100 + 50;
int result4 = 7 + 9;
```

The addition operation itself is simple.

But imagine the logic were more complicated:

```text
calculate tax
validate account
calculate average
check password
format report
```

If we repeatedly write the same logic:

```text
logic
logic
logic
logic
```

we create duplication.

Methods allow us to conceptually create something once:

```text
calculateTax()
```

and then use that operation whenever we need it.

```text
calculateTax()
      ↑
      │
 ┌────┼────┐
 │    │    │
use  use  use
```

So the second major purpose is:

> **Methods allow us to reuse logic.**

---

# 4. Method Boundaries

This is an important concept.

A method creates a **boundary** around a piece of logic.

Think of it like a box:

```text
┌──────────────────────────┐
│       calculateTax()     │
│                          │
│   tax calculation logic  │
│                          │
└──────────────────────────┘
```

The rest of the program doesn't need to deal with every individual step inside that box.

It can think:

```text
"I need the tax calculation."
        ↓
calculateTax()
```

This is called **abstraction** at a very basic level.

You don't necessarily need to know how the operation works internally every time you use it.

---

# 5. A Real-World Analogy

Think about a coffee machine.

You don't manually control:

```text
heat water
↓
pump water
↓
mix coffee
↓
control temperature
↓
dispense coffee
```

You interact with:

```text
MAKE COFFEE
```

The machine hides the internal steps behind a boundary.

Methods can provide a similar boundary in a program.

```text
makeCoffee()
```

could represent:

```text
heat water
pump water
mix coffee
dispense coffee
```

The caller only needs to know:

```text
makeCoffee()
```

This doesn't mean methods magically hide everything. It means we can **organize complexity into meaningful units**.

---

# 6. The Main Idea

For this lesson, remember this model:

```text
WITHOUT METHODS

main()
│
├── logic
├── logic
├── logic
├── logic
├── logic
├── logic
└── logic
```

versus:

```text
WITH METHODS

main()
│
├── getInput()
├── calculate()
├── validate()
└── displayResult()
```

The second structure gives us:

* **Separation of responsibilities**
* **Reusable logic**
* **Clear boundaries**
* **Smaller pieces of code**
* **Easier debugging**
* **Easier maintenance**
