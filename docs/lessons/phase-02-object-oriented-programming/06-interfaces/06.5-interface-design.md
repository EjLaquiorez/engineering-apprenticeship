Consider two possible designs.

Design A — Separate interfaces

- `Describable` declares `describe()`.
- `Printable` declares `print()`.
- `Borrowable` declares `borrow()`.

Each class implements only the interfaces it needs.

Design B — One combined interface

- `LibraryItemActions` declares all three methods.
- Every class implements `LibraryItemActions`, even if some operations don't apply to it.

## Exercise 35A — Review

1\. Why choose Design A?

Correct. Each class implements only the capabilities it needs.

- `Book` implements `Describable`, `Printable`, and `Borrowable`.
- `Magazine` implements `Describable` and `Borrowable`.
- `LibraryReport` implements `Describable` and `Printable`.

This keeps each interface focused and avoids forcing classes to support unrelated operations.

2\. What happens if `LibraryReport` must implement `borrow()`?

You mentioned that the method might “just go null when processed.” You're thinking in the right direction: the class would have to provide a method that doesn't make sense for it.

However, there's an important Java distinction:

- Java requires a concrete class to implement every abstract method inherited from an interface it implements.
- The class could provide an empty method, but that would silently do nothing.
- It could throw an `UnsupportedOperationException`, but then the method exists even though the operation isn't supported.

Neither is a good design when the class shouldn't have that capability in the first place.

This relates to the Interface Segregation Principle (ISP): clients and classes shouldn't be forced to depend on operations they don't use or need.

## Exercise 35B — Review the Contract

Now let's test whether you can recognize a poorly designed interface.

Imagine this interface:

```
interface LibraryActions {
    void describe();
    void print();
    void borrow();
    void returnItem();
    void calculateLateFee();
}
```

A `LibraryReport` only needs `describe()` and `print()`. It doesn't represent a borrowable item, so borrowing, returning, and late-fee calculations don't apply.

Your task — no code required:

1. What is the main design problem with `LibraryActions`?
2. How would you improve it? You can reuse `Describable`, `Printable`, and `Borrowable`, or suggest another focused interface if necessary.

Explain your reasoning in your own words. I want you to identify the design problem before we start writing code.

Correct! ✅ You've identified the main problem: the interface combines too many capabilities, even though some classes don't need them.

Let's sharpen your understanding a little.

An interface can contain many methods without automatically being poorly designed. The problem is that `LibraryActions` groups different responsibilities together and forces implementing classes to provide methods they don't need.

For example, `LibraryReport` needs `describe()` and `print()`, but it shouldn't need to implement `borrow()`, `returnItem()`, or `calculateLateFee()`.

### How would you improve it?

Split the interface into focused capabilities:

- `Describable` — `describe()`
- `Printable` — `print()`
- `Borrowable` — `borrow()` and `returnItem()`
- `LateFeeCalculable` — `calculateLateFee()`

Notice that `Borrowable` and `LateFeeCalculable` are separate because being borrowable doesn't necessarily mean an object needs to calculate late fees.
