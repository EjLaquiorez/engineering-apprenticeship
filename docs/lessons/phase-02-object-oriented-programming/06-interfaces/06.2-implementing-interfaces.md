## 1. A new way to refer to objects

In Exercise 31C, you wrote:

```
Book book = new Book();
Report report = new Report();
```

These variables use their concrete class types.

But because both classes implement `Summarizable`, Java also permits:

```
Summarizable book = new Book();
Summarizable report = new Report();
```

Let's understand why this matters.

- `new Book()` creates a `Book` object.
- `Summarizable book` declares a reference whose type is the interface.
- `book.summarize()` calls the implementation provided by the actual object.

The interface reference exposes the behavior promised by the contract without requiring the calling code to depend on the concrete class.

## 1. Code review

Different implementations of the same interface

`Book` and `Magazine` both implement `Describable`, but each class defines its own `describe()` behavior. This correctly demonstrates that an interface establishes a contract, not identical output.

Good use of encapsulation

Your fields are `private final`, and your constructors initialize them. This protects the fields from direct external modification and ensures the required values are provided when creating each object.

Interface references

```
Describable book = new Book("Clean Code", "Robert C. Martin");
Describable magazine = new Magazine("National Geographic", 42);
```

These variables use the interface type as the reference while the actual objects are `Book` and `Magazine`. This is valid Java and demonstrates interface polymorphism.

### One small design note

Using `getClass().getSimpleName()` is valid and avoids repeating the class name in the output. For this exercise, it works well. In a larger application, though, consider whether a method should depend on the object's runtime class name or whether the class should explicitly define the description format it owns.
