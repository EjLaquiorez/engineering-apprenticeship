## 3. The concept you'll learn

You've already worked with polymorphism using your notification system:

```
Notification[] notifications = {
    new EmailNotification(),
    new PushNotification(),
    new SMSNotification()
};

for (Notification notification : notifications) {
    notification.send();
}
```

Your `Notification` parent class already provides a common type. But consider a design question:

What if every notification must provide its own `send()` implementation, and a generic notification should never be instantiated on its own?

That is where abstraction becomes useful.

An abstract class can define a common contract while leaving certain implementation details to its child classes. You'll learn how to express that in Java rather than simply copying a pattern.

What you got right:

One important clarification: You wouldn't necessarily need to change the whole `LibraryItem` class. The problem is that its code could accumulate more and more item-specific conditions, making it harder to manage.

For example, imagine a growing list of conditions:

```

    // borrowing rule for books
} else if (itemType.equals("Magazine")) {
    // borrowing rule for magazines
} else if (itemType.equals("DVD")) {
    // borrowing rule for DVDs
}
```

If you add `ResearchJournal`, you might need another condition. Imagine maintaining dozens of these!

Design B allows each item type to provide its own rule while sharing a common abstraction.

## Review of your answer

You said:

> it easier to maintain because having only one way to calculate the borrowing days is so much work if do many time duplicate

You're partly correct, but there's a distinction to understand.

The goal is not to make every item calculate the same number of borrowing days. A book might be borrowed for 14 days, a magazine for 7 days, and a DVD for 3 days.

Instead, the goal is to give every item a consistent way to ask for its borrowing period.

Think of it this way:

- `Book` calculates its borrowing period using book-specific rules.
- `Magazine` calculates its borrowing period using magazine-specific rules.
- `DVD` calculates its borrowing period using DVD-specific rules.
- The library system calls `calculateBorrowingDays()` without needing to know which item it is processing.

This is where abstraction becomes powerful: one common requirement, multiple possible implementations.

You also mentioned duplication. Abstraction can help reduce duplication, but it doesn't automatically eliminate it. We still need to decide which behavior should be shared and which should be different.

## Lesson 27 · Review of your final answer

Your answer is B — correct! ✅

You chose to require the developer to implement `calculateBorrowingDays()` before `ResearchJournal` can be used as a concrete library item.

Here's why that is a good design decision:

- Consistency: Every concrete library item provides the same required method.
- Reliability: The library system can call that method without worrying that a particular item type forgot to implement it.
- Flexibility: Each item type can calculate a different borrowing period.
- Maintainability: Java can catch a missing implementation at compile time when the class is declared as a concrete subclass of an abstract class.

That last point is especially important. Java's abstract classes let us express requirements in code rather than relying only on developer discipline.

Your understanding is developing well. One refinement: abstraction is about exposing essential behavior while hiding implementation details. Reducing duplication and improving maintainability are possible benefits, not the definition itself.

Compare the four OOP concepts you've studied:

- Encapsulation: Controls access to internal state.
- Inheritance: Establishes parent–child relationships.
- Polymorphism: Lets a common reference work with different object implementations.
- Abstraction: Defines essential behavior without requiring every implementation detail to be specified in the common type.
