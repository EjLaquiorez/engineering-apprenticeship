## 3. The concept you'll learn

You've already worked with polymorphism using your notification system:

```
Notification[] notifications = {
    new EmailNotification(),
    new PushNotification(),
    new SMSNotification()
};

for (Notification notification : notifications) {
    notification.send();
}
```

Your `Notification` parent class already provides a common type. But consider a design question:

What if every notification must provide its own `send()` implementation, and a generic notification should never be instantiated on its own?

That is where abstraction becomes useful.

An abstract class can define a common contract while leaving certain implementation details to its child classes. You'll learn how to express that in Java rather than simply copying a pattern.

## Review of your answer

You said:

> it maybe harder to maintain because youll be needing change the whole code of the LibraryItem just to add an item every time

What you got right:

- Adding new item types could require repeatedly modifying `LibraryItem`.
- As more item types are added, the general class could become harder to maintain.
- Changes to existing rules could accidentally affect other item types.

One important clarification: You wouldn't necessarily need to change the whole `LibraryItem` class. The problem is that its code could accumulate more and more item-specific conditions, making it harder to manage.

For example, imagine a growing list of conditions:

```
if (itemType.equals("Book")) {
    // borrowing rule for books
} else if (itemType.equals("Magazine")) {
    // borrowing rule for magazines
} else if (itemType.equals("DVD")) {
    // borrowing rule for DVDs
}
```

If you add `ResearchJournal`, you might need another condition. Imagine maintaining dozens of these!

Design B allows each item type to provide its own rule while sharing a common abstraction.
