## 2. Lesson 30 — Concept 1: What belongs in the abstract parent?

An abstract class is not automatically a good design just because several classes can extend it.

The design question is: What do these classes genuinely have in common, and what must each child do differently?

Let's revisit your Lesson 29 payment example.

Payment — abstract parent

Shared behavior: printReceipt()

Required behavior: processPayment()

CashPayment

Implements cash payment processing.

CardPayment

Implements card payment processing.

Notice the division of responsibility:

- Parent class: Contains behavior that can genuinely be shared, such as printing a receipt.
- Abstract method: Defines behavior every concrete child must provide, such as processing a payment.
- Child class: Implements the behavior specific to its own payment type.

You already demonstrated this successfully in `Exercise29C`. Lesson 30 asks you to make these decisions yourself when designing a class hierarchy.

### A practical design rule

Consider a parent class when its child classes represent meaningful variations of the same general concept.

For example, `CashPayment` and `CardPayment` are both types of `Payment`. But that does not mean every method belongs in `Payment`.

Suppose you add this method to the parent:

```
public void swipeCard() {
    System.out.println("Swiping card.");
}
```

Would that make sense for `CashPayment`? No. The behavior is specific to card payments, so it belongs in `CardPayment`, not in the shared parent.

Also, avoid creating an abstract class simply because two classes happen to contain similar code. Consider whether they represent the same underlying concept and whether the shared design makes the program easier to understand and maintain.

## Question 1 — Concrete vs. abstract methods

Your answer:

> because printing receipt method is same on every type of transaction while processingPayment is not where it needs their own implementation

Correct — you understand the main distinction.

You identified the key difference:

- `printReceipt()` is concrete because the parent provides a shared implementation that child classes can inherit.
- `processPayment()` is abstract because each concrete payment type must provide its own implementation.

One important refinement: an abstract method doesn't necessarily mean the behavior is completely unrelated between child classes. It means the parent declares the required behavior without providing its implementation.

For example, both cash and card payments process payments, but they may do so differently.

Mentor question: Could `CashPayment` inherit `printReceipt()` without overriding it? Why?

## Question 2 — Deciding what belongs in the parent and children

Your answer:

> ill put the parent class a method eat because that the only thing that dog and cat do same and animal sound as on child class

Correct design direction.

You correctly placed:

- `eat()` in `Animal`, because it represents shared behavior.
- `bark()` in `Dog` and `meow()` in `Cat`, because those behaviors are specific to each child.

One refinement: dogs and cats don't necessarily eat in exactly the same way. The important point is that eating is a behavior they can share at the level of the `Animal` abstraction. The parent can provide a general implementation, while child classes may override it if they need different behavior.

Also, an abstract parent doesn't have to contain only shared methods. It can declare abstract methods that require child classes to provide their own behavior.

For instance, you could declare `makeSound()` as abstract in `Animal` and implement it differently in `Dog` and `Cat`.
