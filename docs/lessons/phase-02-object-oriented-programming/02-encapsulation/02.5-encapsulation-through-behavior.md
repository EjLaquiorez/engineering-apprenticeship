### 🎯 Lesson Goal

Today we're going to move beyond:

> "Private fields + getters/setters"

and learn a more important OOP idea:

> **The object should control its own data and rules.**

---

# 1. Think About a Bank Account

Suppose we have:

```java
class BankAccount {
    private double balance;

    double getBalance() {
        return balance;
    }

    void setBalance(double newBalance) {
        balance = newBalance;
    }
}
```

We can do:

```java
account.setBalance(5000);
```

But now imagine:

```java
account.setBalance(-1000);
```

We could add validation:

```java
void setBalance(double newBalance) {
    if (newBalance >= 0) {
        balance = newBalance;
    }
}
```

That's better.

But there's a deeper question:

### Should a bank account really have a generic `setBalance()`?

Think about how a real bank account works.

You don't normally say:

> "Set my balance to ₱5,000."

Instead, you say:

> "Deposit ₱5,000."

or:

> "Withdraw ₱1,000."

That means the object's **behavior** should represent the real operation.

---

# 2. Generic Setter vs. Behavior

### Generic setter

```java
account.setBalance(5000);
```

This basically says:

> "Here is a value. Put it into your balance."

### Behavior

```java
account.deposit(5000);
```

This says:

> "Perform the operation of depositing ₱5,000."

The second approach gives the `BankAccount` object responsibility for deciding **how a deposit works**.

For example:

```java
void deposit(double amount) {
    if (amount > 0) {
        balance += amount;
    }
}
```

Now the rule belongs to the object that owns the data.

---

# 3. The Object Owns the Rule

Imagine:

```text
Outside Code
     │
     │ deposit(500)
     ▼
┌─────────────────────────────┐
│       BankAccount           │
│                             │
│ private balance 🔒          │
│                             │
│ deposit()                   │
│   └─ checks amount          │
│   └─ changes balance       │
│                             │
└─────────────────────────────┘
```

The outside code doesn't need to know **how** the balance is changed.

It simply says:

```java
account.deposit(500);
```

The `BankAccount` handles the details.

This is **encapsulation through behavior**.

---

# 4. Why This Is Better

Suppose we put the rules outside:

```java
if (amount > 0) {
    account.setBalance(account.getBalance() + amount);
}
```

Now outside code needs to understand how the bank account works.

That's not ideal.

Instead:

```java
account.deposit(amount);
```

The caller doesn't need to know:

* how the balance is stored
* how validation works
* how the calculation happens
* what rules the account follows

The `BankAccount` handles those details.

# Exercise 14A — Identify the Better Design

Look at these two designs.

### Design A

```java
class BankAccount {
    private double balance;

    double getBalance() {
        return balance;
    }

    void setBalance(double newBalance) {
        balance = newBalance;
    }
}
```

Outside code:

```java
account.setBalance(
    account.getBalance() + 500
);
```

### Design B

```java
class BankAccount {
    private double balance;

    double getBalance() {
        return balance;
    }

    void deposit(double amount) {
        if (amount > 0) {
            balance += amount;
        }
    }
}
```

Outside code:

```java
account.deposit(500);
```

# Exercise 14B — Move the Rule Into the Object

Now you'll practice converting a generic setter into meaningful behavior.

Create:

```text
Exercise14B.java
```

Start with:

```java
public class Exercise14B {

    static class BankAccount {
        private double balance;

        double getBalance() {
            return balance;
        }

        void setBalance(double newBalance) {
            balance = newBalance;
        }
    }

    public static void main(String[] args) {

        BankAccount account = new BankAccount();

        account.setBalance(1000);

        System.out.println("Balance: " + account.getBalance());
    }
}
```

### Your task

Change the design so that instead of:

```java
account.setBalance(1000);
```

we can write:

```java
account.deposit(1000);
```

Your `deposit()` method should:

* accept an amount
* only deposit if the amount is greater than `0`
* add the amount to `balance`

For example:

```text
Starting balance: 0

deposit(1000)
        ↓
balance becomes 1000

deposit(500)
        ↓
balance becomes 1500
```

For this exercise, **remove `setBalance()`**.

We want to practice asking:

> "What behavior does this object actually need?"

rather than simply giving outside code a setter for everything.
