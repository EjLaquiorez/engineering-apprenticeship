# Exercise 15A — Find the Encapsulation Problems

Look at this class:

```java
public class Exercise15A {

    static class Student {
        public String name;
        public int age;
        public double grade;

        public void displayStudent() {
            System.out.println(name + " - " + age + " - " + grade);
        }
    }

    public static void main(String[] args) {

        Student student = new Student();

        student.name = "John";
        student.age = -50;
        student.grade = 150;

        student.displayStudent();
    }
}
```

There are several encapsulation problems here.

### Your task

Identify **at least three problems** with this design.

Think about what we learned:

```text
private fields
access modifiers
getters/setters
validation
behavior
```

For each problem, explain **why** it is a problem.

For example, don't just say:

> "`name` should be private."

Instead explain:

> "`name` is public, so outside code can directly change the student's state without going through the Student class."

### Your turn

Find **3 or more problems** in `Exercise15A`.

Correct. ✅ You identified the main problem: all three fields are `public`.

```java
public String name;
public int age;
public double grade;
```

Because they're public, outside code can directly do:

```java
student.age = -50;
student.grade = 150;
```

There is no protection or validation.

### Let's go one level deeper

You found **one category of problem**:

> The fields are publicly accessible.

Now identify **two more problems** in the design.

Look at this:

```java
student.age = -50;
student.grade = 150;
```

**Problem 2:** What is wrong with allowing `age` to become `-50`?

**Problem 3:** What is wrong with allowing `grade` to become `150`?

Explain those two in your own words.


Exactly. ✅

You found the two **business-rule problems**:

```text
age = -50
→ invalid ❌

grade = 150
→ invalid ❌
```

Assuming our rule is:

```text
Age   → 1–120
Grade → 0–100
```

The bigger encapsulation problem is **who should enforce those rules?**

Right now, `main()` can do:

```java
student.age = -50;
student.grade = 150;
```

So the `Student` object has no control over its own state.

### The design we're aiming for

```java
class Student {
    private String name;
    private int age;
    private double grade;

    // controlled access/behavior here
}
```

Then the `Student` class can decide:

```text
"Is this age valid?"
"Is this grade valid?"
"Should I accept this change?"
```

That is the same idea you practiced with `BankAccount`.

# Exercise 15B — Choose the Access Modifiers

Now let's practice deciding **what should be public and what should be private**.

Consider:

```java id="qxq2d8"
class Student {

    String name;

    int age;

    double grade;

    void calculateAverage() {
        // calculation
    }

    void validateGrade() {
        // validation
    }

    void displayStudent() {
        // display information
    }
}
```

Imagine this `Student` class is being used by another class.

For each member, decide whether it should be:

```text
public
private
```

### Members

**1.**

```java
String name;
```

**2.**

```java
int age;
```

**3.**

```java
double grade;
```

**4.**

```java
void calculateAverage()
```

**5.**

```java
void validateGrade()
```

**6.**

```java
void displayStudent()
```

### Your task

For each one, tell me:

```text
1. name → ?
2. age → ?
3. grade → ?
4. calculateAverage() → ?
5. validateGrade() → ?
6. displayStudent() → ?
```

And most importantly, **explain why you chose each one**.

Think about our rule:

> **Give a member the narrowest access that satisfies its purpose.**

Good thinking. ✅ Your choices show that you're applying the **narrowest-access** rule.

Your answer:

```text
name              → private
age               → private
grade             → private
calculateAverage  → private
validateGrade     → private
displayStudent    → public
```

For this exercise, that's a reasonable design. But there's an important nuance:

### `calculateAverage()`

Whether it should be `private` depends on **who needs to use it**.

If `displayStudent()` is the only method that needs the calculation:

```java
public void displayStudent() {
    calculateAverage();
}
```

then:

```java
private void calculateAverage()
```

makes sense.

### `validateGrade()`

Same idea.

If validation is only an **internal helper** used by another method:

```java
private void validateGrade()
```

is appropriate.

So your reasoning is moving in the right direction:

> **Don't make something public just because it's a method. Make it public only when outside code actually needs to use it.**

# Exercise 15C — Replace Unnecessary Setters

Now we're going to make a more difficult design decision.

Look at this:

```java id="p3lvcz"
class BankAccount {

    private double balance;

    public double getBalance() {
        return balance;
    }

    public void setBalance(double balance) {
        this.balance = balance;
    }

    public void deposit(double amount) {
        if (amount > 0) {
            balance += amount;
        }
    }

    public void withdraw(double amount) {
        if (amount > 0 && amount <= balance) {
            balance -= amount;
        }
    }
}
```

We learned in Lesson 14 that `deposit()` and `withdraw()` are meaningful behaviors.

Now consider:

```java
account.setBalance(1000000);
```

That allows outside code to completely replace the balance.

### Think about the problem

A bank account should normally change its balance through operations like:

```text
deposit()
withdraw()
```

rather than:

```text
setBalance()
```

So here's the design question:

### Should `setBalance()` be public?

Choose:

```text
A. Keep it public
B. Make it private
C. Remove it completely
```

And explain **why**.

Don't worry about changing the code yet. I want your reasoning first.
