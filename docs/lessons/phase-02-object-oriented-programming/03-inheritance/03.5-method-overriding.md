# Part 1 — What Does "Override" Mean?

Imagine the parent says:

> "Every animal can make a sound."

So we create:

```java
class Animal {
    public void makeSound() {
        System.out.println("Animal makes a sound.");
    }
}
```

Then we create:

```java
class Dog extends Animal {
}
```

Because `Dog extends Animal`, the Dog inherits `makeSound()`.

So:

```java
Dog dog = new Dog();
dog.makeSound();
```

uses the parent's method.

But perhaps we want a Dog to make a more specific sound.

We can write:

```java
class Dog extends Animal {
    public void makeSound() {
        System.out.println("Dog barks.");
    }
}
```

Now `Dog` has its **own version** of `makeSound()`.

That is **method overriding**.

---

## Think of it this way

### Without overriding

```text
Animal
 └── makeSound()
       "Animal makes a sound."

Dog
 └── inherits makeSound()
```

### With overriding

```text
Animal
 └── makeSound()
       "Animal makes a sound."

Dog
 └── makeSound()
       "Dog barks."
```

The child is saying:

> "I inherited this behavior, but I have a more specific way to perform it."

# Exercise 20C — `@Override`

Now we're going to add something important that you'll see constantly in real Java code:

```java id="p6lv8c"
@Override
```

You already know what this does:

```java id="5fjy7m"
class Dog extends Animal {
    public void eat() {
        System.out.println("Dog is eating.");
    }
}
```

We know `Dog.eat()` is overriding `Animal.eat()`.

We can tell Java explicitly:

```java id="0kr1g5"
class Dog extends Animal {

    @Override
    public void eat() {
        System.out.println("Dog is eating.");
    }
}
```

`@Override` is an **annotation**.

For now, think of it as telling the compiler:

> **"I intend for this method to override a method from the parent class. Please check that I'm actually doing that."**

---

### Why is that useful?

Imagine you accidentally type:

```java id="g8s4h1"
@Override
public void Eat() {
    System.out.println("Dog is eating.");
}
```

Notice:

```text
eat()
Eat()
```

Java considers those **different method names**.

Without `@Override`, Java could treat `Eat()` as a completely new method.

With:

```java id="kw7a5j"
@Override
```

Java tells you:

> ❌ This method does not actually override a method from the parent.

That's very useful because it catches mistakes.

You've now learned:

```text
Method overriding
       ↓
Child provides its own version
       ↓
Same method name
Same parameters
Compatible return type
       ↓
@Override helps Java verify it
```

And you already know how `super` fits into this:

```java
@Override
public void eat() {

    System.out.println("Dog is eating."); // child behavior
}
```

That's a very important OOP pattern.
